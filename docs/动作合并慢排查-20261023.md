## A 结论
算法容器失去了 GPU 访问能力，动作过渡改用 CPU 计算。
宿主机的 RTX 3060 正常，问题位于容器侧。
多段动作需要逐个生成过渡，因此总耗时增加。
本次没有重启服务，也没有修改代码或配置。

## C 为什么 GPU 没有工作
| 检查 | 现场结果 |
| --- | --- |
| 宿主机 NVIDIA 工具 | 正常识别 RTX 3060，驱动 580.178.04 |
| 合并期间宿主机 GPU 使用率 | 0%，未见算法计算进程 |
| 容器内 NVIDIA 工具 | Failed to initialize NVML: Unknown Error |
| 容器内 PyTorch | 2.11.0+cu128，CUDA 12.8 |
| PyTorch CUDA 可用性 | False，设备数为 0 |
| 容器 GPU 配置 | 已请求 NVIDIA GPU 0，设备节点存在 |
| 合并期间算法 CPU 占用 | 约 402%，相当于四个 CPU 核心 |
代码检测不到 CUDA 时会自动选择 CPU。
设备配置存在，不能证明容器仍能访问 GPU。
具体失效触发原因仍未确认。

## D 为什么短过渡也要等
每个非零过渡都单独调用动作扩散模型 MDM。
当前模型配置每次需要 50 步采样。
模型输入固定为 196 帧，短过渡也要走采样循环。
任务 1180 有 16 个非零过渡，需要串行生成。
合并过程还会反复转换已经合并的动作。

因此，0.05 秒的过渡并不等于 0.05 秒的计算。
源码位置：vendor/mdm/merge.py、vendor/mdm/workbench/transitions.py。

## E 已排除与证据边界
源码与模型的 NVMe 挂载仍存在。
算法容器已经运行六天，不是刚启动的服务。
因此，手册中的模型机械盘冷读问题不是首要解释。
宿主机交换空间已满，但采样期间没有持续换页。
另一个容器占用约四核 CPU，可能增加竞争。
当前证据不足以量化这些因素的影响。

健康检查只证明 HTTP 服务存活，没有证明 GPU 可用。
训练日志中的 Token 未配置属于另一条任务路径。
日志没有每个合并阶段的耗时，不能精确拆分 90 秒。

## F 建议处理顺序
先确认当前没有进行中的合并任务。
在维护窗口重启算法容器，尝试恢复 GPU 访问。
重启后检查容器 NVIDIA 工具和 PyTorch CUDA。
若仍失败，再检查 NVIDIA 容器运行时和设备权限。
需要重建容器时，保留现有挂载和环境配置。
恢复后用相同输入复测，比较总耗时与 GPU 使用率。

长期建议：GPU 不可用时告警，避免静默使用 CPU。
同时记录下载、预处理、等待、采样和回调耗时。
以上均为建议，本次没有执行恢复操作。
